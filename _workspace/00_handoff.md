- **저장한 기록 수정(M16):** 기록 상세 → [수정] → S8 `/meal/:mealId/edit`(결과 수정 화면 수정 모드). 음식별 값·추가·삭제는 결과 수정 규칙 그대로, 끼니와 날짜(오늘과 지난 날짜만)도 수정. 사진 재분석 없음(DB에 없는 이름으로 바꿀 때만 호출 D). 규칙에 `done → done` 전이, `editedAt`(수정 시각, "수정됨" 표시), `createdAt` 불변. 규칙을 바꾸면 테스트 추가 후 다시 배포.
- **하루 요약 필수(축소 대상 아님):** 홈에 오늘 기록을 끼니별(아침·점심·저녁·간식)로 음식 이름·kcal과 함께, 기록을 누르면 상세 S7 `/meal/:mealId`(음식별 무게·남긴 비율·인원·kcal·탄단지·출처, 읽기 전용), 날짜 이동 ◀ 전날 / 다음 날 ▶(오늘이면 다음 날 비활성, 오늘이 아니면 [오늘로]), 기록 삭제(확인 후). 저장한 기록 수정은 아래 M16.
- **목표 설정 화면(S6 `/goal`):** 성별·나이(14~100)·키·몸무게·활동량(5단계 계수 1.2~1.9)·목표(감량/유지/증량) → Mifflin-St Jeor로 기초대사량·하루 소모량 → 목표 kcal(감량 −400, 유지 ±0, 증량 +300)과 탄단지(감량 50:25:25, 유지·증량 55:20:25). 2026-10-27 사용자 결정으로 바꿈(전: 감량 −500, 모두 55:20:25). AI 호출 없음. 계산은 `web/src/analysis/goal.ts` 순수 함수.
- **하루 요약 비교:** kcal·탄·단·지 "먹은 양/목표" 막대와 남은 양(넘으면 "초과"). 목표가 없으면 "목표 설정하기" 카드.
- **안전 장치:** 목표 kcal은 기초대사량 아래로 내리지 않는다. 만 18세 미만은 목표를 유지로 고정하고 안내한다. "의학적 조언이 아니에요" 고지.
- **수정·직접 조정(사용자 추가):** 설정은 언제든 고치고 바로 재계산. 추천 kcal·탄단지는 직접 조정 가능, kcal 하한은 성인 기초대사량·만 18세 미만 하루 소모량, [추천값으로] 버튼.
- **저장:** 현재 설정은 `users/{uid}` 문서의 `goal` 필드, 날짜별 목표 기록은 `users/{uid}/goals/{dateKey}`(목표를 저장한 날짜, 같은 날은 덮어씀, 신체 정보 없이 목표값만). 어떤 날의 비교 목표 = 그날 이전 가장 늦은 기록. 2단계 조각 3의 보안 규칙은 meals만 다루고, 목표 규칙은 3단계에 더한다.
- **주간 추이(S9 `/week`, M17):** 최근 7일 꺾은선, 탭(칼로리|탄|단|지), 그날 목표 점선, 기록 없는 날 빈칸, ◀ 지난주 / 다음 주 ▶. 홈에서 링크로 연다(리더 결정, 바꿀 수 있음). 스펙 4.7절 끝.
- **프리미엄 기능(3단계 뒤 따로, 지금은 만들지 않음):** 남은 영양소 기반 음식 추천, 월간 그래프, 리포트. 발표에서는 프리미엄 계획으로 소개(5단계 pitch-writer).
- **Gemini 지연(2026-10-26 23시 KST 측정):** 같은 사진으로 a2 12.9초, a3 40.1초·16.8초(낮에는 a1·a2 4~6초). a3 응답 형식은 정상(`whole_count: 1`). 2026-10-27 사용자 결정으로 호출 A·B 시도당 제한을 40초로 늘리고 시간 초과는 재시도하지 않게 바꿨다(스펙 4.2).
- 오늘 실제 호출 누적(에이전트·리더): 0단계 4, 1단계 4, 공개 중량 a3 4(시간 초과 1 포함), 그 밖 사용자 브라우저 시험.
- 일정 위험: 3단계에 하루 요약·목표·주간 추이·기록 수정이 함께 들어간다. 밀리면 스펙 6.3 축소안 0(기록 수정 → 4단계), 0-1(주간 추이 칼로리 탭만), 3(목표 막대 kcal 한 줄) 순서로 쓴다.

## 4. 이번 세션에서 정한 것 (`CLAUDE.md`에 있는 것은 요약만)
- 기본 모델 `gemini-3.5-flash-lite`, 검색 단계(그라운딩)는 코드만 두고 기본 꺼짐. 무료 등급에서 3.5 Flash-Lite 그라운딩은 429, 2.5 Flash-Lite는 신규 사용자 404였다(`03_vision_eval.md` "스파이크").
- 식약처 DB에서 100ml 기준 값만 있는 음식은 1ml=1g으로 환산해 넣고 출처를 "DB 환산"(2026-10-27 시안 문구로 바꿈)으로 구분한다. 국·음료처럼 원래 환산하던 행도 같은 표시다. Gemini는 중량을 g으로 추정한다.
- 종류별 차이가 큰 음식(햄버거·샌드위치, 치킨, 피자, 떡볶이·라면, 마라탕·샐러드, 카페 음료, 케이크·디저트)
  - Gemini가 보이는 특징까지 구체적인 이름으로 답한다(프롬프트 a2).
  - DB에서 세부 종류(이름)까지 맞을 때만 DB 값을 쓴다. 대표값이나 일반 이름에만 맞으면 "AI 추정" 값을 쓰고 DB 값은 "참고 DB 대표값 ○○kcal/100g (이름)"으로만 보인다.
  - 사용자가 자동완성이나 세부 종류 목록에서 고르면(`dbCode`) 이 규칙 없이 DB 값을 쓴다.
- 별칭: 통째 15개 + 단어 치환 9개(치킨→닭튀김, 계란→달걀, 까스→가스, 라테→라떼, 쇠고기→소고기 등, `03_vision_eval.md` "별칭·세부 종류"). "치킨"은 대표값에만 맞아 AI 추정 + 참고 301kcal, "양념치킨"·"간장치킨"·"후라이드 치킨"은 세부 행이 있어 DB.
- 프롬프트 버전: 호출 A `a2`, B `b1`, D `d1`. `remaining_ratio`는 **남은** 양(0 = 다 먹음, 1 = 그대로).
- 먹기 전 사진은 먹은 후 분석이 **성공했을 때만** IndexedDB에서 지운다(실패하면 다시 시도할 수 있게 남긴다). 먹은 후 사진은 메모리에만 둔다.
- 같은 사진 안내: 먹은 후 사진이 먹기 전과 같으면(압축본 SHA-256) 분석 호출 **전에** "먹기 전과 같은 사진이에요"를 띄우고, [그대로 분석]을 눌러야 호출한다.
- 결과 수정 화면에서 스펙과 다르게 정한 점(`02_frontend_notes.md`): "5+"는 5~20 입력, 남긴 비율을 모를 때 "다 먹음" 버튼, 새 항목은 이름칸에 포커스·100g, 카드 순서는 처음에만 정렬.
